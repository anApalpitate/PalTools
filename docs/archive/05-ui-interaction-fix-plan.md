# UI 与交互问题修复计划

## 1. 背景与目标

本轮修复面向图鉴、配种查询和配种路径规划中的 9 项 UI/交互问题。目标是在不改变现有核心数据和配种算法语义的前提下，改善详情弹窗、帕鲁选择器、筛选排序、工作适应性和本地保存体验。

本计划仅用于整理实施范围和验收口径，不将当前工作区中的候选改动直接视为已完成。

## 2. 当前基线

- 技术栈：React 19、TypeScript、Vite、Electron。
- 主要界面集中在 `src/App.tsx`，样式集中在 `src/styles.css`。
- 图鉴筛选与排序逻辑位于 `src/domain/pals.ts`。
- 本地配置和“已拥有帕鲁”序列化逻辑位于 `src/domain/config.ts`。
- 工作适应性图标需要经过 `pipeline/data/paldb/` 抓取、`pipeline/data/build.ts` 构建和 `pipeline/data/validate.ts` 校验后进入 `public/data/`。
- 当前工作区存在未提交修改，其中已有覆盖多项需求的候选实现。实施时必须先保留这些修改，并以逐项验收和补缺为主，不能覆盖或回退无关改动。

### 2.1 已确认的产品口径

- 主要验收目标为 Windows Electron 桌面端，覆盖 1920×1080、1366×768，以及 100%/125% 系统缩放；浏览器版保持基本响应式可用。
- 桌面常用尺寸下仅主动技能框滚动；窄屏或低高度窗口允许弹窗内部响应式内容区滚动，但背景页面始终锁定。
- 提升所有承载有效信息的次级文字；英文名、数据来源等辅助信息继续保持较弱视觉层级。
- 重新打开帕鲁选择框时显示全部候选并定位当前项，同时全选输入文字。
- 工作适应性采用 AND 多选，彻底移除“适性最低等级”筛选项。
- 工作适应性提供“全部/清空”入口；卡片保留全部适性，并突出当前命中的适性。
- 数值排序支持升序/降序，和其他过滤同时生效；缺失值始终排在最后，卡片显示当前排序字段。
- 所有应用内滚动区域统一主题滚动条，但不修改操作系统级设置。
- “已拥有帕鲁”采用小型圆形头像标签；未保存修改在离开路径页或关闭软件前给出提醒。
- 最少代数模式隐藏指定代数框；切回指定代数时保留最近一次合法值。

## 3. 修复项与验收标准

### 3.1 图鉴详情仅技能区域滚动（第一阶段已完成）

**问题**

打开帕鲁详情后，滚轮会带动整个页面或整个详情弹窗，用户无法稳定查看左侧基础资料。

**方案**

- 打开详情时锁定页面 `body` 滚动，关闭详情时恢复原状态。
- 桌面布局中固定详情弹窗及左侧资料区域，只给“主动技能”面板设置纵向滚动。
- 技能标题保持吸顶，滚动时始终可见。
- 为技能面板设置 `overscroll-behavior: contain`，防止滚动传递到弹窗和背景页。
- 窄屏或低高度窗口中优先保持背景页不滚动；若固定资料无法完整容纳，则只允许弹窗内部的响应式内容容器滚动，并保留技能面板独立滚动能力。

**验收**

- 桌面常用尺寸下，鼠标位于技能区域时仅技能列表滚动。
- 鼠标位于左侧资料区时，背景页面不会随滚轮移动。
- 打开和关闭弹窗后，页面原有滚动位置不跳动。
- `Esc`、关闭按钮和点击遮罩关闭均能正确恢复页面滚动状态。

### 3.2 提升属性等文字的可读性（第一阶段已完成）

**问题**

属性类型、字段标题、来源说明和部分技能信息颜色偏暗、字号偏小。

**方案**

- 统一调整详情弹窗中的次级文字色，不再使用与深色背景对比不足的灰绿色。
- 重点提升以下区域：属性类型、伙伴技能说明、数值名称、数值来源、工作适应性、技能标签、攻击范围和技能描述。
- 过小文字整体提升约 1–2 px；普通正文原则上不低于 12 px，关键标签不低于 11 px。
- 保留主信息、次信息和弱提示三级层次，避免所有文字都使用同一亮度。
- 检查 100%、125% 和 150% 系统缩放下是否截断或重叠。

**验收**

- 属性名称和类型无需悬停即可清楚辨认。
- 字号增大后，卡片和详情布局不溢出、不遮挡。
- 普通正文与背景对比度以 WCAG AA 的 4.5:1 为目标；装饰性或禁用态文字不纳入该要求。

### 3.3 配种工具下拉列表支持滚动选择（第一阶段已完成）

**问题**

原生候选列表在当前桌面环境下无法可靠使用滚轮浏览。

**方案**

- 将帕鲁选择控件统一为受控的自定义组合框，不依赖浏览器 `datalist`。
- 候选面板限制最大高度并启用纵向滚动。
- 支持鼠标滚轮、触控板、滚动条拖动以及键盘方向键。
- 键盘补充 `Home`、`End`、`Enter`、`Escape` 行为，并确保高亮项自动滚入可视区域。
- 正向配种、反向查询、路径目标和起点添加复用同一选择器，避免交互分叉。

**验收**

- 候选数量超过一屏时，可以连续滚动到首项和末项。
- 鼠标点击与键盘选择得到相同结果。
- 滚动候选列表不会带动页面。
- 组合框具备正确的 `combobox`、`listbox`、`option` 和选中状态语义。

### 3.4 再次打开已选帕鲁的选择框时显示全部候选（第一阶段已完成）

**问题**

选择一只帕鲁后再次点击输入框，已有完整名称会继续作为检索词，列表中只剩当前帕鲁，不便切换。

**方案**

- 区分“输入框展示值”和“实际检索词”两个状态。
- 输入框获得焦点或再次点击时：
  1. 清空实际检索词；
  2. 展示全部候选；
  3. 全选输入框中的已有文字；
  4. 将当前已选帕鲁设为键盘高亮项并滚动到可视区域。
- 用户开始输入时，用新文字重新过滤候选。
- 只有在用户选择明确候选时才更新业务选中值；单纯打开列表不清除原选择。

**验收**

- 已选择帕鲁后再次点击，列表立即显示全部帕鲁。
- 原文字处于全选状态，当前项可见；直接输入即可替换并开始新检索。
- 点击外部取消时，原选择保持不变。
- 中文名、英文名和图鉴编号均可用于再次检索。

### 3.5 补充工作适应性图标并改为一行多选（第二阶段已完成）

**问题**

工作适应性缺少图标，筛选形式与属性筛选不一致，且单选不利于组合查询。

**方案**

- 从现有 paldb 来源链路抓取工作适应性图标，并保存来源 URL、文件哈希和本地 WebP 路径。
- 增加工作适应性目录数据，并在 manifest 中记录数量。
- 构建和校验阶段检查名称唯一、图标文件存在、哈希格式正确，以及帕鲁数据中的适性名称都能映射到目录。
- 在图鉴卡片和详情中展示图标；资源失败时提供不破坏布局的占位符。
- 将工作适应性筛选改为与属性筛选相同风格的一行按钮组，采用多选。
- 删除“适性最低等级”标签、下拉框、React 状态和领域过滤参数，不保留隐藏或禁用的旧控件。
- 多选语义确定为 **AND**：帕鲁必须具备全部已选工作适应性，不再比较最低等级。
- 增加“全部/清空”入口；未选择任何适性时等价于不过滤。
- 图鉴卡片继续展示帕鲁的全部适性，对当前选中的适性增加高亮，而不是隐藏未选适性。

**验收**

- 每种工作适应性都有本地图标或明确的降级占位。
- 可同时选择多个工作适应性，选中状态清晰。
- 页面和可访问性树中均不存在“适性最低等级”筛选项。
- 多选与文字搜索、属性筛选和数值排序可以同时生效。
- “全部/清空”能一次清除所有适性条件，卡片能突出命中的适性而不丢失其他适性信息。
- 离线环境中不请求远程图标。

### 3.6 统一滚动条美术风格（第一阶段已完成）

**问题**

默认系统滚动条与深色绿色主题不协调。

**方案**

- 建立可复用的主题滚动条样式，覆盖轨道、滑块、悬停状态和圆角。
- 应用于应用主页面、技能列表、帕鲁候选列表和配种树替代方案等所有应用内滚动区域。
- Firefox 使用 `scrollbar-width` 和 `scrollbar-color`，Chromium/Electron 使用 `::-webkit-scrollbar` 系列样式。
- 保持足够的滑块对比度和可点击宽度，不追求过度纤细。
- 样式只属于 PalTools 页面，不修改操作系统级滚动条设置。

**验收**

- Electron/Chromium 和 Firefox 下颜色、圆角与页面主题协调。
- 滑块默认、悬停状态清楚可辨。
- 横向滚动区域与纵向滚动区域没有样式冲突。

### 3.7 图鉴数值范围过滤改为数值排序（第二阶段已完成）

**问题**

当前最小值/最大值输入操作成本高，也不方便直接比较帕鲁。

**方案**

- 删除数值最小值和最大值输入。
- 增加“排序数值”和“排列方式”：
  - 排序数值：HP、攻击、防御、工作速度、各类移动速度、耐力等已有数值字段；
  - 排列方式：从高到低、从低到高。
- 排序先作用于已经经过文字、属性和工作适应性过滤的结果。
- 数值缺失项始终放在末尾；数值相同则按图鉴编号和内部 ID 稳定排序。
- 选中排序数值后，在图鉴卡片上显示对应字段名称和数值，避免用户只看到顺序变化却不知道依据。
- 未选择排序数值时保持当前默认图鉴顺序。

**验收**

- 不再出现数值最小值/最大值输入框。
- 任一过滤条件变化后，剩余结果仍按当前数值和方向排列。
- 升序、降序结果正确，空值不出现在有效数值之前。
- 卡片显示的数值与排序字段一致。

### 3.8 已拥有帕鲁显示头像并增加显式本机保存（第二阶段已完成）

**问题**

已拥有列表仅显示文字，辨识速度较慢；增删后自动保存也不利于用户确认变更。

**方案**

- 将已拥有帕鲁展示为带小型圆形头像、中文名和删除按钮的紧凑标签组件。
- 标签悬停提示英文名和图鉴编号，不在常态布局中额外占用空间。
- 分离“当前编辑列表”和“已保存列表”，通过序列化结果判断是否有未保存变更。
- 增加“保存到本机”按钮。只有点击按钮后，才把当前列表写入现有 `localStorage` 键。
- 新增和删除都进入未保存状态；保存成功后显示短暂反馈。
- 刷新应用时仅恢复上次明确保存的内容，未保存修改不写入本机。
- 有未保存修改时，离开路径规划页面或关闭软件前显示确认提醒；用户取消后保留当前编辑内容。
- 临时起点继续保持会话级状态，不出现本机保存按钮。

**验收**

- 已拥有列表中的每个帕鲁都显示小型圆形头像、中文名和独立删除入口，悬停可看到英文名和编号。
- 添加或删除后出现“有未保存更改”提示，刷新后恢复上次保存版本。
- 点击保存后，本次所有添加和删除结果一起持久化。
- 保存按钮在没有变更时禁用，连续点击不会产生重复数据。
- 存在未保存修改时，离开路径页和关闭应用都会提示；保存后不再提示。

### 3.9 最少代数模式隐藏指定代数输入框（第一阶段已完成）

**问题**

选择“最少代数”后仍显示右侧“指定代数”输入框，容易让用户误以为该值会参与计算。

**方案**

- 仅在“指定代数”模式下渲染代数输入框，而不是只做视觉禁用。
- 最少代数模式下将查询区域从三列收缩为两列，避免留下空白。
- 切换回指定代数时保留最近一次合法值；管理员降低上限时继续执行现有纠正逻辑。

**验收**

- 最少代数模式下 DOM 中不存在“指定代数”输入框。
- 指定代数模式下输入框恢复显示且可用。
- 两种模式切换后布局稳定，路径计算使用正确参数。

## 6. 验证策略与耗时控制

为避免命令和校验长时间占用对话，采用分层验证：

### 快速层：每个小改动后

- 只运行 TypeScript 静态检查或直接相关的单个测试文件。
- 不在每次样式微调后执行完整数据校验、完整构建或 EXE 打包。
- 命令达到预设时间仍无结果时先读取当前输出，判断是正常计算、等待网络还是异常挂起。

### 长期服务管理：强制要求

- Vite、preview、watcher 等长期服务不得使用 `start /b`、`Start-Process`、`cmd /c start`、`nohup` 或其他脱离当前执行上下文的后台方式启动。
- 必须使用能够返回并管理 `cell_id` 的长任务执行机制：以前台方式启动服务，执行器短暂让出后记录 `Script running with cell ID ...`。
- 服务输出只通过该 `cell_id` 增量读取，不因暂时没有新输出而重复启动服务。
- 浏览器检查或依赖该服务的任务结束后，必须使用同一 `cell_id` 明确终止，并确认测试端口已经释放、就绪 URL 已不可访问。
- Windows 下 npm 可能派生不会随 cell 一起退出的 `node`/Vite 子进程，因此不能只凭 cell 已终止判断服务已关闭。
- 若端口仍被监听，应从该端口解析准确 PID，核对可执行文件和启动时间属于本项目服务后，仅终止该 PID。
- 若执行被中断，恢复工作时先检查现有 cell 或准确端口，再决定终止或重启；不得按进程名称批量结束。
- 计划和最终验证记录中必须同时记录服务已启动以及已确认终止。

### 专项层：每个阶段完成后

- UI 交互：运行 `src/App.test.tsx`。
- 筛选排序：运行 `src/domain/pals.test.ts`。
- 本地保存：运行配置测试和对应 UI 用例。
- 数据抓取与构建：只运行 paldb 解析测试和数据校验。

### 最终层：全部修复完成后

- TypeScript 全量检查。
- 全量测试。
- 数据完整性校验。
- Web 构建。
- Electron 桌面端定向冒烟检查。

如非发布要求，本轮不重复执行耗时的 EXE 打包；确需打包时放在所有代码和数据检查通过之后。

## 7. 回归风险

- **滚动冲突**：响应式断点可能重新允许整个弹窗滚动，需要分别检查宽度和高度断点。
- **组合框状态不同步**：展示文字、检索词和实际选中 ID 分离后，需覆盖取消、清空、重新打开和数据列表变化。
- **工作适应性目录不完整**：来源网站名称或图标结构变化会导致映射失败，必须由构建校验阻止静默缺图。
- **排序稳定性**：空值和同值项目若无稳定兜底，会在重新渲染时跳动。
- **保存语义变化**：从自动保存改为显式保存后，必须给出明确的未保存状态和离开提醒，避免用户误以为已经落盘或误丢修改。
- **现有未提交改动**：本轮实施前已有大范围代码和生成数据变更，任何修复都应基于差异逐项补齐，不能通过重置工作区获得“干净基线”。
