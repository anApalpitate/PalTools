# 配种图性能优化实施复盘

## 1. 复盘范围

本文复盘 2026-08-01 完成的配种图性能与交互优化，代码提交为 `76d3c34 feat: optimize breeding forest viewport`。该轮工作将 React Flow 替换为固定森林槽位、轻量 HTML/SVG 渲染和统一视口变换，并完成缩放、适应画布、工具光标、覆盖式侧栏、配方追加按钮、测试、浏览器回归、文档和提交。

本文关注执行过程本身：哪里耗时最多、哪里占用上下文和 Token 最多、哪些尝试无效，以及后续如何以更短路径得到同等或更可靠的结果。

## 2. 耗时分析

### 2.1 最耗时：临时 Playwright 性能验收

浏览器阶段是绝对的耗时中心。日志中可直接观察到的长调用包括约 44、52、65、84、77、39、143 和 126 秒，累计已超过 10 分钟，尚未计入命令准备、失败定位和结果阅读时间。

主要原因：

1. 当前工具环境没有直接暴露适合长期前台服务的终端 cell，因而每次尝试都临时启动静态服务、创建 Playwright CLI 会话、加载 300 个帕鲁及其素材，结束后再关闭服务。
2. 为构造 500 节点方案，先后尝试了 `run-code`、IndexedDB 注入、`eval` 和同步批量点击。多段嵌套异步函数被 CLI 解析器拒绝，批量点击又未形成有效的 500 节点样本。
3. 每轮失败都包含浏览器启动、数据加载和大量本地素材请求，反馈周期远长于单元测试。
4. 验收目标同时包含节点构造、FPS、长任务、光标、侧栏、缩放、适应画布、响应式、破图、控制台和请求边界，单次脚本承担的职责过多，语法或前置状态失败时整轮结果作废。

最终只有多尺寸溢出、破图、控制台、第三方请求和基础页面结构得到可靠浏览器结论；500 节点 50 FPS 没有被无效注入“伪装成通过”，而是明确保留为未完成的浏览器性能验收。这一处理是正确的，但应更早停止重复尝试。

### 2.2 第二耗时：大组件替换后的编译—测试迭代

`BreedingGraphCanvas.tsx` 一次性替换约 560 行，随后出现了导入错误、旧接口测试桩、侧栏接口和动画时间基准等问题。这里的单次反馈并不慢：TypeScript 通常约 6–7 秒，定点测试约 14–25 秒；但集中替换导致多个错误同时出现，增加了定位轮次。

其中最典型的问题是视口动画使用 `performance.now()` 作为起点，而 jsdom 的 `requestAnimationFrame` 时间戳与其时间基准不一致，测试中缩放被钳制到 `0.2`。改为在第一帧记录起点后解决。该问题说明动画纯逻辑应先独立验证，再接入组件。

### 2.3 必要但可控：完整交付门

完整测试约 38 秒，25 个测试文件、195 项测试通过；数据校验约 15 秒；生产构建约 11–13 秒。它们虽然有固定成本，但结果稳定、价值明确，不是主要浪费来源。

有效的节奏是：领域定点测试 → 组件定点测试 → TypeScript → 完整测试/数据校验 → 最终生产构建。问题在于后续又调整了布局缓存和可访问标签，导致生产构建需要再执行一次。以后应在完整交付门前设置“代码冻结点”。

## 3. Token 与上下文消耗分析

环境未提供精确的逐工具 Token 计量，因此无法给出可靠的绝对数字。以下按输出规模和进入模型上下文的内容做相对判断。

### 3.1 最大来源：完整浏览器快照

配种图侧栏默认包含 300 个帕鲁。对整个页面执行 `snapshot` 后，单次输出曾达到约 4,960 行和 1,874 行；大量内容只是重复的头像、名称、编号和“加入画布”按钮。这些输出对定位工具栏和画布几何几乎没有增量价值，却占用了最多的上下文。

优化原则：

- 进入配种图后先过滤侧栏到 1–3 项，或先关闭侧栏，再生成快照。
- 优先对工具栏、画布或弹窗目标执行局部 snapshot。
- 已知文本时使用 `find` 获取局部上下文，不读取整棵可访问性树。
- 几何、计算样式、溢出和破图直接返回紧凑 JSON，不把 DOM 全量序列化。

### 3.2 第二来源：一次读取多篇完整文档

文档收尾阶段一次读取 `docs/README.md`、产品、架构、路线图和根 README，工具输出超过 10,000 tokens 且被截断。真正需要修改的只是少数“React Flow”“侧栏”“缩放”段落。

优化原则：先用 `Select-String` 定位关键词和上下文，只打开命中的局部段落；只有需要理解完整结构时才读取全文。文档索引可完整读取，长产品和架构文档应按章节读取。

### 3.3 第三来源：长文件整段输出与重复状态输出

完整输出 `BreedingGraphWorkspace.tsx`、大段 CSS 和 Canvas JSX，叠加多次 `git diff --stat`、换行符警告及重复测试日志，也消耗了较多上下文。代码检索应优先使用符号、类名和接口关键词，只读取命中位置前后 20–80 行。

## 4. 做得有效的部分

1. 先将 `todolist` 变更单独提交，避免需求文档与实现提交混杂。
2. 先抽取森林布局和视口纯函数，并为 100/300/500 节点建立确定性测试，再替换 UI。
3. 用 TypeScript 尽早发现旧 `updatePositions` 和 `onRegisterAddAtCenter` 接口残留。
4. 定点测试始终先于完整测试，避免在早期反复支付完整 jsdom 测试成本。
5. 移除 React Flow 时同步清理 package lock 和旧样式，并验证源码和锁文件不再引用该依赖。
6. 对未完成的 500 节点浏览器 FPS 验收如实记录，没有用领域基准替代浏览器结论。
7. 最终更新产品、架构、路线图、todolist 和完成记录，并执行链接检查和 `git diff --check`。

## 5. 可优化的执行流程

### 5.1 在编码前定义可执行的性能夹具

本轮只有领域层 100/300/500 节点夹具，没有可被浏览器稳定载入的方案文件或测试入口。后续涉及大图性能时，应在编码前准备：

- 确定性的 `.paltools-plan.json` 性能夹具，或仅在开发/测试构建启用的本地夹具加载入口；
- 100、300、500 节点各一份，包含离散节点、横向森林、纵向森林和多树；
- 固定的验收脚本直接导入夹具，不依赖 UI 连续点击或临时 IndexedDB 注入。

这样可以把“构造状态”和“测量性能”分离，避免验收脚本同时承担数据生成职责。

### 5.2 浏览器回归拆成三个小闭环

不要用一个长脚本同时验证所有目标：

1. 结构与功能：侧栏开合、工具切换、缩放边界、适应画布、配方 `+` 按钮。
2. 几何与质量：五种视口、溢出、破图、控制台、第三方请求。
3. 性能：加载固定 100/300/500 节点夹具，只测 FPS、长任务、可见节点数量和交互后视口持久化。

任何一组失败时只重跑对应闭环。

### 5.3 在长浏览器调用前做语法和能力探针

本轮在完整页面加载后才发现 `run-code` 复杂脚本解析失败。改进顺序应为：

1. 用最小页面或当前页面执行 1 行 `run-code`/`eval` 探针。
2. 在本地用 JavaScript 解析器检查待执行函数语法。
3. 先验证 IndexedDB 的单次读取和写入，再扩展到 500 节点。
4. 最后才启动完整计时回归。

若同一工具限制连续出现两次，应切换为固定测试脚本或明确记录阻塞，不继续堆叠临时命令。

### 5.4 将组件替换拆成可编译的中间步骤

更稳妥的顺序：

1. 新增布局和视口纯函数及测试。
2. 新增轻量视口组件，但暂不删除旧组件。
3. 让工作区切换到新组件并通过 TypeScript/组件测试。
4. 再移除旧接口、React Flow 样式和依赖。
5. 最后完成侧栏和配方按钮交互。

这会短暂保留未使用代码，但每一步错误面更小，避免一次替换 500 余行后同时处理接口、样式和测试问题。

### 5.5 设置代码冻结点，减少重复交付门

建议在以下事项全部完成后再运行完整测试和生产构建：

- API 与依赖清理完成；
- 组件定点测试通过；
- 可访问名称与文案确认；
- 缓存和性能路径完成代码审查；
- 文档行为描述已起草。

冻结后只允许修复交付门发现的问题。这样通常只需一次完整测试和一次最终构建。

## 6. 推荐的下一次执行模板

1. 阅读任务相关入口、工作区状态和现有 diff。
2. 建立验收矩阵，区分领域、组件、浏览器和发布门。
3. 先创建可复用性能夹具及纯函数测试。
4. 以可编译中间步骤替换组件，每步运行最窄测试。
5. 清理旧依赖和死接口，执行 TypeScript。
6. 用三个独立浏览器闭环完成结构、几何和性能验收；失败两次即审查工具路线。
7. 代码冻结后执行完整测试、数据校验和生产构建。
8. 定向更新文档，执行链接检查和 diff 检查。
9. 核验提交范围并创建单一实现提交。

## 7. 核心结论

上一轮的主要成本并非森林布局算法或 React 组件实现，而是缺少可直接载入的浏览器性能夹具，导致状态构造与性能测量耦合，并引发多轮高延迟、低信息密度的 Playwright 尝试。下一次同类任务最有价值的优化，是先把大规模测试状态变成稳定输入，再让每个浏览器脚本只回答一个问题。同时严格限制快照和长文档输出范围，可以显著降低 Token 消耗并保留更多有效上下文。
